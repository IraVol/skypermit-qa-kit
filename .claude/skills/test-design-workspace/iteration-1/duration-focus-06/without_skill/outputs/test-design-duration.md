# Тест-дизайн: TIME_WINDOW — тривалість вікна польоту (TSD-4 §3)

**Джерело:** `specs/06-business-rules.md`
**Обсяг:** лише умова *Duration* гейту `TIME_WINDOW`. Lead time, advance booking, curfew, overlap — поза обсягом (використовуються тільки як «нейтральні» умови в тестових даних).

## 1. Що каже специфікація (дослівно)

| # | Цитата | Рядок |
|---|---|---|
| Q1 | "Duration \| 15–240 minutes, inclusive at both ends. `window_end` strictly after `window_start`. \| `TSD-4` §3" | 95 |
| Q2 | "`TIME_WINDOW` \| Duration out of range \| `TSD-4 §3`" | 188 |
| Q3 | "Gates run in a fixed order and evaluation stops at the first failure: **`PILOT` → `AIRCRAFT` → `ZONE` → `TIME_WINDOW`**" | 24–26 |
| Q4 | "`failing_gate` in a `422` response always names the *first* gate to fail, never every gate that would fail." | 28 |
| Q5 | "`window_start`/`window_end` are stored and compared in UTC." | 99 |

Тестована величина: **D = window_end − window_start, у хвилинах**.

- Валідно: 15 ≤ D ≤ 240 (Q1, обидві межі включні).
- Невалідно: D < 15, D > 240, а також D ≤ 0 (Q1, "strictly after").
- Очікувана відмова: `422`, `failing_gate = "TIME_WINDOW"`, `rule_reference = "TSD-4 §3"` (Q2). Текст `message` специфікацією не задано — перевіряємо лише, що він непорожній.

## 2. Класи еквівалентності (EP)

| ID | Клас | Діапазон D (хв) | Представник | Очікування | Підстава |
|---|---|---|---|---|---|
| EP-1 | Валідна тривалість | 15…240 | 90 | гейт проходить, немає 422 | Q1 |
| EP-2 | Занадто коротке, end > start | 1…14 | 5 | 422 / TIME_WINDOW / TSD-4 §3 | Q1, Q2 |
| EP-3 | Занадто довге | > 240 | 360 | 422 / TIME_WINDOW / TSD-4 §3 | Q1, Q2 |
| EP-4 | Нульове вікно (end = start) | 0 | 0 | відмова (див. U-1 щодо коду/посилання) | Q1 "strictly after" |
| EP-5 | Інвертоване вікно (end < start) | < 0 | −60 | відмова (див. U-1) | Q1 "strictly after" |
| EP-6 | Валідне вікно через північ UTC | 15…240, дата end = дата start + 1 | 23:30Z → 01:00Z (90) | гейт проходить | Q1 + Q5 (порівняння в UTC; тривалість — різниця моментів, а не годин доби) — *виведено, прямо не сказано* |
| EP-7 | Дуже довге, багатоденне | ≫ 240 | 1 440 (24 год) | 422 / TIME_WINDOW / TSD-4 §3 | Q1 — перевіряє, що немає переповнення/порівняння лише годин |

## 3. Граничні значення (BV)

Межі задані включно в хвилинах (Q1). Для кожної межі — трійка (межа−1, межа, межа+1).

| ID | Межа | D (хв) | Очікування |
|---|---|---|---|
| BV-1 | нижня 15 | **14** | 422 / TIME_WINDOW / TSD-4 §3 |
| BV-2 | нижня 15 | **15** | проходить |
| BV-3 | нижня 15 | **16** | проходить |
| BV-4 | верхня 240 | **239** | проходить |
| BV-5 | верхня 240 | **240** | проходить |
| BV-6 | верхня 240 | **241** | 422 / TIME_WINDOW / TSD-4 §3 |
| BV-7 | "strictly after" (0) | **−1** | відмова (U-1) |
| BV-8 | "strictly after" (0) | **0** | відмова (U-1) |
| BV-9 | "strictly after" (0) | **1** | 422 / TIME_WINDOW / TSD-4 §3 (end > start, але < 15) |

Примітка: межа «strictly after» повністю накрита нижньою межею 15 — будь-яке D ≤ 0 також < 15. Окремо вона цікава лише тим, що система може відхиляти D ≤ 0 інакше (раніше, іншим кодом) — див. U-1.

Опційні проби точності (лише якщо API приймає секунди — U-2):
- BV-10: D = 14 хв 59 с → очікувано відмова
- BV-11: D = 240 хв 01 с → очікувано відмова

## 4. Взаємодія з порядком гейтів

Тривалість перевіряється в останньому гейті, тому відмова `TIME_WINDOW` видна лише коли `PILOT`, `AIRCRAFT`, `ZONE` проходять (Q3, Q4).

| ID | Дані | Очікування | Підстава |
|---|---|---|---|
| GO-1 | D = 360 (EP-3) + висота 150 м у зоні зі стелею 120 м (ZONE падає) | 422, `failing_gate = "ZONE"`, `rule_reference = "ZC-2026.1 §2"` — **не** TIME_WINDOW | Q3, Q4, рядок 183 |
| GO-2 | D = 5 (EP-2) + рейтинг пілота `R_BASIC` у зоні `CONTROLLED` (PILOT падає) | 422, `failing_gate = "PILOT"`, `rule_reference = "OH-1 §2.1"` | Q3, Q4, рядок 180 |

## 5. Переходи станів (ST)

Не застосовуються в межах цього правила: умова тривалості — чиста функція від `window_start`/`window_end`, специфікація 06 не прив'язує її до станів запиту. Життєвий цикл (що стається із запитом при відмові на submit) описано в окремій специфікації (02 — Request Lifecycle) і тут не виводиться.

## 6. Базові тестові дані («все інше валідне»)

Щоб відмова гарантовано походила від тривалості, усі інші умови мають проходити:

| Параметр | Значення | Чому |
|---|---|---|
| Зона | `DNI-OPN-1` (або `KHR-OPN-4`) | `OPEN`, стеля 120 м, C0–C3, `L1`, **без curfew** (рядки 109, 157) — curfew не зачепить навіть 24-годинне вікно |
| Пілот | будь-який рейтинг, `certified_on` так, щоб на `window_start` минуло < 18 міс. | `OPEN` приймає будь-який рейтинг; currency (рядок 41) |
| Повітряне судно | напр. 800 г (C0) | дозволено в зоні |
| Оператор | `authorisation_level` ≥ `L1` | рядок 83 |
| Висота | 50 м | ≤ 120 |
| `window_start` | now + 2 доби (UTC) | ≥ 6 год lead time, ≤ 60 днів advance (рядки 93–94) |
| Overlap | нове ПС або вікна, що не перетинаються з `APPROVED`/`UNDER_REVIEW` того ж ПС | рядок 97 |
| `window_end` | `window_start` + D | змінна тесту |

Для EP-6 `window_start` = (now + 2 доби) з часом 23:30Z.

## 7. Невідомі — специфікація мовчить (не вгадувати)

| ID | Питання | Вплив |
|---|---|---|
| U-1 | Як відхиляється D ≤ 0: як `422 TIME_WINDOW / TSD-4 §3` на validate/submit, чи раніше — на запис запиту (напр. `400`)? Специфікація лише каже "strictly after" поряд із діапазоном. | Очікування для EP-4, EP-5, BV-7, BV-8 — уточнити в API Contract (03). |
| U-2 | Точність часу: хвилини чи секунди? Чи 14:59 «округлюється»? | Чи потрібні BV-10/BV-11. |
| U-3 | Порядок підумов всередині `TIME_WINDOW` (lead time / advance / duration / curfew / overlap) не задано. Якщо невалідні одночасно тривалість і, напр., lead time — який `rule_reference` повернеться? | Не будувати кейси на комбінації двох порушень TIME_WINDOW; ізолювати тривалість (розд. 6). |
| U-4 | Текст `message` для порушення тривалості. | Перевіряти лише наявність, не зміст. |
| U-5 | Успішна відповідь validate (код/тіло) у 06 не описана. | «Проходить» = немає 422; точний код — з 03. |
| U-6 | Відсутній `window_end` / null — не описано в 06. | Поза цим дизайном; належить контракту API. |

## 8. Підсумок покриття

- EP: 7 класів (3 валідні/невалідні основні + 0, від'ємні, північ UTC, багатоденне)
- BV: 9 значень (3 трійки) + 2 опційні проби точності
- Порядок гейтів: 2 кейси
- ST: не застосовно (обґрунтовано)
- Невідомі: 6

Мінімальний набір без дублювання (якщо треба скоротити): BV-1…BV-6, BV-8, EP-3 (360), EP-5 (−60), EP-6, GO-1.
